# FakeGlucoSense

A portfolio project that simulates a continuous glucose monitor (CGM). A JVM TCP simulator,
an Android phone acting as a BLE sensor, or ESP32/NimBLE firmware can supply synthetic readings
to a separate Android companion app. The Android/JVM code is Kotlin; the ESP32 is a C++ port of
the sensor model and BLE wire format.

- **Companion (`app`):** Room history, 3 / 6 / 12 / 24-hour Compose chart, trend arrows
  (`↑↑ ↑ ↗ → ↘ ↓ ↓↓`), threshold and rapid-change notifications, foreground monitoring,
  and periodic WorkManager checks.
- **JVM simulator (`simulator`):** TCP/NDJSON stream, seeded scenarios, configurable cadence,
  speed, and backfill. Best route for an emulator demo.
- **Phone sensor (`sensor-app`):** a second, BLE-peripheral-capable Android phone advertising
  the Bluetooth SIG CGM Service (`0x181F`).
- **ESP32 (`esp32/`):** firmware advertising the same service. **Its synthetic clock is not
  synchronized with the companion's clock; connecting works, but the stock companion's
  current-day chart will not show its readings.** See [ESP32 limitations](esp32/README.md#limitations).

> **Not a medical device.** All readings are synthetic, generated by a teaching model. Never
> use this software, its alerts, or anything derived from it for treatment decisions.

## Quick start

Commands below run from the repository root. You need JDK 17+ for Gradle; the Android SDK for
`app` and `sensor-app` (both minSdk 26, compile/targetSdk 36); and PlatformIO plus an ESP32
board only for firmware. See [Build and test](#build-and-test).

### 1. Run the simulator (JVM, no Android SDK needed)

```bash
./gradlew :simulator:run --args="--port 8765"
```

In another terminal, connect with `nc localhost 8765`. A new client first receives the
configured backfill, then live readings. Example lines (illustrative timestamps/values):

```json
{"t":1791784200000,"mgdl":106,"direction":"NOT COMPUTABLE","seq":0}
{"t":1791784500000,"mgdl":104,"direction":"Flat","rate":-0.400,"seq":1}
```

`t` is UTC epoch milliseconds; `rate`, when present, is mg/dL/min. The first reading in a
session has no computable trend. `seq` is the session's reading index, not the BLE time offset.

Options (`./gradlew :simulator:run --args="--help"` shows the full CLI):

| Option | Default | Meaning |
|---|---|---|
| `--port` | `8765` | TCP port; `0` chooses an available port. |
| `--bind` | `0.0.0.0` | Listen address; by default other devices on the LAN can connect. |
| `--scenario` | `MEAL_DAY` | `STEADY`, `MEAL_DAY`, `NOCTURNAL_LOW`, `HIGH_SPIKE`, `ACTIVE_DAY`. |
| `--seed` | `42` | Reproducible model seed for the same scenario, start time, and time zone. |
| `--speed` | `1` | Multiplier, 0.1–3600; at 60× a 5-minute reading arrives every 5 seconds. |
| `--interval-minutes` | `5` | Simulated minutes between samples, 1–60. |
| `--backfill-hours` | `24` | History replayed to each new client, 0–168 hours. |
| `--zone` | system zone | Local time zone for scheduled meals, e.g. `Europe/Berlin`. |

TCP is unencrypted; only run it on a trusted network. `--bind 127.0.0.1` limits access to
the host machine (including an emulator that reaches it through `10.0.2.2`).

### 2. View it in the Android emulator

1. Start the JVM simulator on your computer; install and launch the **`app`** module.
2. The default source is **Simulator (TCP)** at `10.0.2.2:8765`, the computer as seen by the
   Android emulator. For a physical phone, change the host in **Settings** to the computer's
   LAN address and leave the simulator listening on a LAN-reachable interface.
3. On the **Glucose** tab, tap **Start monitoring**. There is no monitoring switch in Settings.
   On Android 12+ the app requests `BLUETOOTH_CONNECT` even for TCP, because its foreground
   service uses the `connectedDevice` type. Android 13+ also asks for notification permission;
   without it the service can run, but notifications/alerts may be hidden.
4. The chart fills from the simulator's backfill, then updates as readings arrive. When
   notifications are allowed, the service's ongoing notification has a Stop action; the
   **Glucose** tab also has **Stop monitoring**.

### 3. Try BLE with two phones

1. On a phone that supports BLE peripheral advertising, install `sensor-app`. Choose a scenario
   and speed and tap **Start sensor**; grant Bluetooth permissions. Real time (1×) gives the
   most meaningful current-time chart and stale-data check. At 60× the sensor's timestamps
   eventually run ahead of the companion's clock.
2. On a different phone, install `app`. In **Settings → Data source**, select **BLE sensor**,
   tap **Scan for sensors**, and pick the advertising phone. Grant the requested permissions.
3. On the companion's **Glucose** tab tap **Start monitoring**. It requests stored records
   over RACP and subscribes to live CGM Measurement notifications, verifying E2E-CRC when
   present. The phone sensor prepopulates about 24 hours of simulated history at startup.

### 4. Try an ESP32 board (with a clock limitation)

```bash
pip install platformio
pio run -d esp32 -t upload
pio device monitor -b 115200
```

The PlatformIO configuration targets `esp32dev` with NimBLE-Arduino. The board advertises as
`FakeCGM` and can be selected in the companion's BLE scan. It starts with **empty history**
and builds up to 300 readings as it runs; a large report at the default BLE MTU may be partial.
Its session starts at a *synthetic* 2026-01-01 UTC epoch, not today's date. The companion does
not set the sensor's Session Start Time, while its chart and stale check compare readings to
the phone's real clock. **Use the TCP or second-phone sensor to demo the live chart today**;
selecting the board only demonstrates the GATT link/record delivery until time sync is fixed.
See the [firmware guide](esp32/README.md) for serial commands and limitations.

The on-air format is the [project's v2 implementation](docs/ble-protocol.md) of a **subset of
CGMS v1.0.2**, including status annunciation, E2E-CRC, RACP, and session/cadence ops.
“v2” labels this project's implementation revision, **not** a Bluetooth SIG v2 standard.

## Features and layout

| Feature | Code / notes |
|---|---|
| Seeded physiology model and five scenarios | `core`'s `sim` package, `simulator`, `sensor-app`; C++ analogue in `esp32/` |
| Nightscout-named trend bands (15-minute least-squares slope) | `core`'s `analysis.TrendCalculator`, ADR-0005 |
| Low/high/urgent and rapid-change alerts with hysteresis and reminders | `core`'s `analysis.AlertEvaluator`, ADR-0010 |
| Chart, time-range controls, stats, and mg/dL or mmol/L display | `app`'s `ui` package, `core`'s `analysis.GlucoseStats` |
| Room timestamp de-duplication and 30-day retention | `app`'s `data.db` and `work.RetentionWorker` |
| Foreground live link, 15-minute periodic stale check | `app`'s `service` and `work` packages (checks may be delayed by Android) |
| BLE central and two BLE peripheral implementations | `app`'s `data.ble`, `sensor-app`'s `ble`, `esp32/` (see clock caveat above) |
| Urgent/general alert, monitoring, and stale-data notification channels | `app`'s `notify.AppNotifications` |

```text
core/           Pure Kotlin/JVM: glucose model, BLE codecs, trend and alert logic, JSON wire
simulator/      JVM CLI: TCP/NDJSON server using the core model
app/            Android companion: Compose, Room, WorkManager, foreground service, BLE central
sensor-app/     Android BLE peripheral backed by core/sim
esp32/          Separate PlatformIO project with C++ sensor/wire ports
docs/           Current plan, architecture, BLE protocol, research notes, and historical ADRs
```

## Build and test

```bash
./gradlew :core:test :simulator:test                                  # JVM tests
./gradlew :app:assembleDebug :app:testDebugUnitTest                    # Android SDK
./gradlew :sensor-app:assembleDebug :sensor-app:testDebugUnitTest      # Android SDK
pio run -d esp32                                                      # PlatformIO firmware build
./gradlew lint                                                        # optional local lint, not in CI
```

[CI](.github/workflows/ci.yml) runs the JVM tests, both Android debug builds/unit tests, and
the firmware **build** on pushes and PRs. It does **not** run lint, ESP32 host-vector tests, an
emulator, or physical BLE tests. See [verification and remaining work](docs/PLAN.md).
